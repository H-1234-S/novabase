## 多租户架构评审（Schema-per-Project 追问）

对 4 个追问做了基于源码的核查，结论：

- 全仓库唯一 `search_path` 设置点是 `apps/api/src/sql-editor/sql-editor.service.ts:126`，用 `SET LOCAL` 包在 `neonSql.transaction([...])` 里；Drizzle 用 `drizzle-orm/neon-http`，无客户端连接池，所以"连接还池残留 search_path"这个洞当前不存在（靠驱动无状态，不是靠设计）。
- 但存在更严重的洞：SQL 编辑器用 `DATABASE_URL`（schema owner）执行任意 SQL，`SELECT * FROM other_schema.t` 直接可读；黑名单只拦 3 个前缀。`public.projects` 里存着明文 `anon_key`/`service_role_key`，`public.users` 有 `password_hash` → 单项目编辑器权限可升级为全平台。
- 全仓库无 `CREATE ROLE` / `GRANT` / `row_security`（已 grep 确认），即没有任何数据库层权限隔离，只有命名空间隔离。
- `generateDbSchema()` 用 `randomBytes(4)`（32bit），1 万项目时 birthday 碰撞概率约 1.1%，且 `db_schema` 有 unique 约束但无重试 → 直接 500。
- `provisionSchema()` 只 `CREATE SCHEMA`，不建任何基线表，也没有租户级 migration ledger；drizzle-kit 只管 `public`。
- 修复主线：per-project DB role + `SET LOCAL ROLE`，让越权由 42501 拒绝而非文本检查。

## Realtime 重连与数据补偿（14-fixes 分支）

- 重连是三层：Socket.IO 默认值自动重连（客户端未显式配置）、`connect` 时用 `subscribedRef` 重放 subscribe（5s ACK 超时，失败即踢出订阅列表）、`RealtimeService` 对 LISTEN 连接做 500ms×2^n 封顶 30s 的指数退避重建，并通过 `LISTENER_RECONNECTING` / `LISTENER_CONNECTED` 上报状态。
- 数据补偿在 21:27 之后才落到工作树：`realtime-client.tsx` 的 `syncTableSnapshot`，触发点为首次订阅、Socket 重连补订阅成功、`LISTENER_CONNECTED`、手动 Refresh；走 `GET /projects/:slug/rest/:table?limit=1000` + anon key + `no-store`，顺序是"先订阅后读快照"以避免盲区。
- 已知边界：服务端 `query-parser.ts:93` 硬顶 1000 行且客户端不传 `order`，大表快照是任意 1000 行；无 cursor/outbox，不能补逐条事件；SDK `packages/novabase/src/realtime` 没有快照能力。
- 注意：`fixes/realtime/execution-flow.md` 描述的是修复前实现（称"没有重连"），已与源码不符。

## 产出：Realtime outbox + cursor 实现 prompt

- 文件：`.workbuddy-ai/prompts/realtime-outbox-cursor.md`，供外部模型执行。
- 关键设计决策：outbox 建在项目 schema（`_rt_outbox`，bigint identity seq），不进 public/不写 drizzle migration；触发器内 `pg_advisory_xact_lock(hashtextextended(projectId:table))` 串行化 seq 分配，否则「seq 分配顺序 ≠ 提交顺序」会导致水位推进后丢事件；订阅载荷升级为 `{table, since?}` 并兼容裸字符串；补投时序为 subscribe(LISTEN) → 第一遍补投 → join room → 第二遍补投 → ACK；seq 用十进制字符串传输避免 bigint 精度丢失。
- 附带要求：`table-editor.getTables()` 过滤 `_rt_%` 内部表，否则内部表泄漏到 UI。
