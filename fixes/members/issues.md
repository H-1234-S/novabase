# 组织成员与邀请问题

## [MEMBER-001] 成员角色与删除操作可跨组织修改成员

- **优先级**：P1
- **问题类型**：授权绕过 / 多租户隔离
- **涉及文件**：`apps/api/src/members/members.controller.ts`、`apps/api/src/members/members.service.ts`
- **涉及位置**：`PATCH :memberId/role`、`DELETE :memberId`；`updateRole()`、`removeMember()` 的 `where(eq(orgMembers.id, memberId))`
- **问题描述**：`OrgRoleGuard` 只确认调用者是 URL 中组织的管理员；服务更新/删除时只按全局唯一 memberId 过滤，没有把 `orgSlug` 与目标成员所属组织一起约束。
- **触发条件**：组织 A 管理员获得或猜到组织 B 的成员 UUID 后，对 A 的成员路由提交该 UUID。
- **根因分析**：守卫授权的是 A，但 service 的目标行来自 B；`ensureNotLastAdmin(orgSlug, memberId)` 只对降级/移除前做按 slug 查询，后续 update 仍无组织约束，因此无法弥补越权，且跨组织 ID 若恰为管理员可被错误计入 last-admin 判断。
- **影响范围**：任意组织成员角色、组织 B 最后一位管理员及其访问能力。
- **修复建议**：在更新/软删除语句中通过组织 slug 对应 orgId 做 `UPDATE ... WHERE member_id AND org_id`，或先以组织范围加载目标行并在同一事务内更改；last-admin 检查也应锁定并限定该组织。
- **验证方式**：A 管理员对 B 成员 ID 发起改角色/删除返回 404/403；同组织合法操作成功；不能移除另一组织管理员。
- **置信度**：已确认

## [MEMBER-002] 最后一位管理员保护存在并发竞态

- **优先级**：P1
- **问题类型**：并发一致性 / 业务逻辑
- **涉及文件**：`apps/api/src/members/members.service.ts`
- **涉及位置**：`ensureNotLastAdmin()` 与 `updateRole()`、`removeMember()` 的分离读写
- **问题描述**：最后管理员校验先读取活跃管理员列表，再单独更新。两个管理员同时降级/移除时，各自都能看到至少两名管理员并通过校验，最终组织可能没有管理员。
- **触发条件**：仅剩两位管理员时并发对两人的角色降级或删除请求。
- **根因分析**：校验与变更之间没有事务锁、串行化保护或数据库约束；应用层读后写在并发请求下不是原子操作。
- **影响范围**：组织失去管理权限，无法再邀请或管理成员。
- **修复建议**：把组织行/管理员集合锁定并在事务中校验和更新；必要时对组织管理员变更串行化。保持跨组织资源限定（参见 MEMBER-001）。
- **验证方式**：并发屏障测试同时提交两次管理员降级/移除，断言始终至少有一名活跃管理员。
- **置信度**：已确认

## [MEMBER-003] 邀请邮件发送失败会被吞掉并返回“成功”

- **优先级**：P2
- **问题类型**：异常处理 / 业务可靠性
- **涉及文件**：`apps/api/src/members/invite.service.ts`
- **涉及位置**：`mailer()` 中 `sendMail` 的空 `catch`；`sendInvite()` 最后返回成功
- **问题描述**：SMTP 发送异常被空 catch 忽略，接口仍回复 `{ message: 'Invite sent' }`。`transporter.verify()` 的回调也未纳入发送流程，错误只输出日志。
- **触发条件**：SMTP 凭据错误、网络故障或收件服务器拒绝。
- **根因分析**：邮件作为关键副作用没有返回结果或持久化待发送任务；异常边界将失败转换成成功响应。
- **影响范围**：组织管理员无法判断邀请是否发出，用户收不到邀请且无法自行重发/追踪。
- **修复建议**：至少传播发送错误并返回明确失败；更可靠方案是写入邀请记录/outbox，再异步发送并支持重试/状态查询。删除每次发送时不等待的 `verify` 或改为启动健康检查。
- **验证方式**：mock SMTP reject，接口不得返回成功；验证失败记录可重试，成功邮件链接对应同一邀请。
- **置信度**：已确认

## [MEMBER-004] 未注册受邀者会创建无密码账户但没有完成注册入口

- **优先级**：P1
- **问题类型**：业务逻辑 / 邀请流程
- **涉及文件**：`apps/api/src/members/invite.service.ts`、`apps/api/src/auth/auth.controller.ts`、`apps/api/src/auth/auth.service.ts`
- **涉及位置**：`acceptInvite()` 中 `users` 仅写入 email；`AuthController.acceptInvite()` 接受邀请后只重定向 dashboard；普通注册因 email 已存在而冲突
- **问题描述**：未注册邮箱接受邀请时，系统创建没有 name/passwordHash 的用户和成员关系，但不发登录 cookie，也不提供设置密码/完成注册步骤。用户被重定向到受保护 dashboard 后仍未认证；用注册接口设置密码又会因邮箱已存在而失败。
- **触发条件**：管理员邀请当前不存在于 `users` 表中的邮箱，收件人点击接受链接。
- **根因分析**：邀请接受将建账号和加入组织合并成匿名 GET 副作用，却没有与账户激活、密码设置或登录会话衔接。代码 TODO 也提到邀请注册设计尚未完成。
- **影响范围**：首次受邀用户无法通过邮箱密码进入组织；邀请看似已接受但账户不可用，管理员可能看到已加入成员。
- **修复建议**：邀请接受应进入受邀者注册/设置密码流程，验证一次性邀请后完成账户激活并登录；或要求先注册再接受邀请。避免未认证 GET 直接创建最终账户/成员关系，并确保邀请码单次消费。
- **验证方式**：分别测试已注册和未注册用户；未注册用户接受后能完成密码设置并建立登录会话；未完成流程不能成为活跃成员；邀请 token 过期/重复使用按策略拒绝。
- **置信度**：已确认
